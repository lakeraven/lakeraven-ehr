# ADR 0013: A tenant is exactly one RPMS instance, and an instance is never shared between tenants

**Status:** Proposed. The compliance premise has not been reviewed by counsel and needs that review before this can be Accepted.
**Date:** 2026-10-29
**Amends:** ADR 0007 (decision 1's "one instance may serve several entities", its rejection of "tenancy = the RPMS instance", the partitioning role of its division machinery, and its requirement that the model express a governance domain **narrower** than the covered entity; see Consequences) and, **if ADR 0008 lands** (it is open as #630), ADR 0008 (its "does not settle shared-instance tenants" and the trigger for its sequence step 4). This ADR decides nothing that depends on ADR 0008's text; see Merge order.
**Builds on:** ADR 0010 (authorization derives from RPMS options and keys), ADR 0011 as amended (the request's client is a scope, not an argument; section 6, a system token runs as a named service account), ADR 0012 (the request context carries the tenant; see the note on rule 5 below), lakeraven-ehr#553.
**Requires edits to:** ADR 0011 (its amendment's sentence that the scope reaches "the fibers and threads it starts", its section 1 sentence that `RpmsRpc.client` stays for jobs, and its Context sentence that every RPC goes through one process-wide client), ADR 0012 (rule 5 and the table row that names `BrokerSession`), and rpms-rpc ADR 0006 (its statement that a `Thread.new` inside a scope loses it). See Required gem changes and Open items.

## Context

ADR 0007 made the tenant the covered entity and let the covered entity and the RPMS instance diverge in both directions: one entity on several instances, and several entities on one instance. Because of the second case it required read scoping and `tenant_id` stamping as well as connection selection, and it rejected "tenancy = the instance" for being unable to represent two entities on one instance.

The maintainer's position is that an organization is one RPMS instance, and that two covered entities sharing an instance is not a topology to support. A read under one entity's authority would reach another entity's patients, and the maintainer treats that as a breach. This ADR does not interpret HIPAA or classify any occurrence; that is for counsel. It takes the position as its premise.

The consequence for design is that a shared instance is an error state to refuse, not a case to engineer around. **Refusing it at configuration load is necessary and not sufficient.** A boot check on a topology does nothing about the runtime identity of a request, so this ADR also states the runtime properties the check protects (decisions 6 and 9).

**Part of the runtime guarantee is already built, and this ADR describes only what is still open.** Each signed-in user now runs on their own RPMS connection: `RpmsSessions` holds one connection per browser session and `RpmsUserScope` runs each request inside `RpmsRpc.with_client` on it. A request with no connection of its own, which includes every `system/` token, reaches no RPMS and gets a 503. See "What main does today" for what that closes and for the globals that remain. What is open is a system token's own identity (a named service account), the topology checks, and turning the guarantee into properties that stay true: not undone by a later setter, not inherited by a child, checked at send time and audited.

**This ADR states properties and the tests that prove them. It does not design the gem.** The client mechanism is ADR 0011's: the request's client is scoped with `RpmsRpc.with_client(client) { ... }`, and a call made outside a scope finds no client and raises `RpmsRpc::NotConfiguredError`. At the pinned gem that sentence holds only while no global client is configured: a later setter or `RpmsRpc.mock!` re-opens a fallback (gem change 1), and a thread started inside a scope inherits it (gem change 2). Each gem change below is named by the property it must give and is specified and gated in its own rpms-rpc issue, so a mechanism flaw is found and fixed there and does not hold this decision.

**ADR 0012 rule 5 and ADR 0011 now disagree, and this ADR flags it without editing 0012.** Rule 5 says the request context is an argument, "no thread-local, fiber-local or global holds it", and ADR 0012's table names `BrokerSession` as the explicit carrier of the client. `BrokerSession` was never built: the door is `RpmsSessions` and `RpmsUserScope`. Amended ADR 0011 carries the *client* in a scope. The split this ADR uses: **ADR 0011 governs how the client reaches the gem** (a scope); **ADR 0012 rule 5 governs the request context** (principal, scopes, tenant), which stays an explicit argument. The scope also carries, as its own state and set when it opens, the identity the request expects and the audit fields (decision 9); that is the scope's state, not a second ambient carrier, and it is why a call with no expected identity is refused (with one stated exception, the sign-on scope, decision 6c). The parenthetical in rule 5 that rejects the ambient approach "for the client", and the table row that calls `BrokerSession` an argument carrier, are stale under this split and need an edit to ADR 0012, which is the maintainer's to make.

## What main does today

Measured on `main` at 3528f31. "The pin" is the rpms-rpc revision in this repo's `Gemfile.lock`, 6723a7f, which carries `RpmsRpc.with_client`.

- **A signed-in browser user.** `RpmsUserScope` (an `around_action` on `WebController` and `ChartsController`) runs the request inside `RpmsSessions.with_user(key)`, so `RpmsRpc.client` is that user's own connection (`rpms_user_scope.rb:26-34`, `rpms_sessions.rb:63-67`). The gateways, `RpcSupport.broker` and every gem module resolve it. **Closed:** a browser request no longer runs as the last clinician to sign in.
- **A `system/` token or any API request.** No scope is opened, so `RpmsRpc.client` raises and `ApplicationController` answers 503, "no RPMS connection of its own" (`application_controller.rb:104-112`), until backend clients have service accounts (ADR 0011 section 6). **Closed:** a system token never runs on a clinician's connection. **Open:** it has no connection of its own at all, and nothing ties one to its tenant (decision 4).
- **Authorization identity.** `current_duz` is nil unless the token is a browser SSO token (`smart_authentication.rb:416-427`). That covers system tokens, and also any non-browser user or patient token.
- **Boot.** Outside the test environment the engine configures **no** global client: it builds the per-user pool (`engine.rb:74-80`, `rpms_sessions.rb:41-44`) and `RpmsSessions.assert_single_process!` refuses to boot with more than one Puma worker, reading `::Puma.cli_config` and `WEB_CONCURRENCY` (`rpms_sessions.rb:93-105`). It returns without configuring anything if a client is already set (`engine.rb:61`) and boots with no backend on a blank host (`:63-66`). **In the test environment it installs one global client when `config/rpms.yml` names a host** (`engine.rb:76`): the live suite's shared client, with `VISTA_RPC_HOST` blank in CI.
- **Globals that still exist.** The test suite installs a mock as the process-global at load (`test_helper.rb:231`) and again before every example (`global_store_isolation.rb:21`); `use_broker` (`test_helper.rb:309-314`) swaps the global for a scripted fake. A development-only spike initializer calls `RpmsRpc.mock!` and installs a global mock in a process that serves requests (`zz_spike_mock_rpc.rb:20`). `README.md:63` tells a host app it may set `RpmsRpc.configure { |c| c.client = ... }` and that "the engine leaves a configured client alone". Wherever a global exists, a call outside a scope runs on it, and ADR 0011's last-clinician case is possible there.
- **Most calls skip the audit wrapper.** Gateways mostly call `RpmsRpc::*` directly, so the audit wrapper is not on those paths, as ADR 0007 already records. `RpcSupport.broker` (`app/gateways/lakeraven/ehr/rpc_support.rb:34`) has 16 call sites, and the wrapper's own header (`audited_broker.rb:24-34`) says that closing the rest needs a client hook in the gem, not more wrappers in the engine.
- **Count of call paths.** Three populations resolve `RpmsRpc.client` underneath. A one-line grep sees only the first.
  - **Direct module calls.** `RpmsRpc::<Module>.<method>` in `app` and `lib`, full-line comments excluded: 53 lines in 21 files (87 lines in 34 files counting comments). Five are `RpmsRpc::FilemanDateParser`, a pure parser with no client, so about 48 resolve a client.
  - **Gateways that inject the module as a default.** The repo's standard gateway style is `def self.x(..., via: default_provider)` with `default_provider` returning an `RpmsRpc::*` module, then `via.method(...)`. The direct-call grep does not match it. Counting `via.<method>` call lines: **88 in 23 gateway files**, from 34 `via: default_provider` signatures in the 16 files that define `default_provider`.
  - **Direct client reads.** `RpmsRpc.client` or `RpmsRpc.configuration.client` is read in `backend_registry.rb:140`, `authentication_service.rb:135` and `:143`, `web_controller.rb:113` and `engine.rb:61`.

  So the population is **roughly 140 sites** over at most 44 files. The two counts above are different methods (module calls versus `via.` calls) and neither is exact; the decisions do not depend on the figure, and no acceptance test below is built from a grep.
- **The binding.** `oauth_applications.organization_id` is a free-form string column. It is blank-checked at mint (`backend_services_controller.rb:62`) and read by the interim guard (`:285-290`). Nothing else reads it.
- **The interim guard** refuses to mint once a second distinct organization is registered. It compares `strip.downcase` strings, not endpoints, so two labels that point at one broker would not trip it.

## Decision

1. **Tenant and instance are one to one.** Each tenant has exactly one *active* instance, and each instance is active for exactly one tenant. An entity that runs two live instances is two tenants. A move between instances is not that case; see decision 7. *Enforced:* within one deployment's configuration. *Promise:* across deployments. Two deployments (two application hosts) that point at one RPMS instance are invisible to both, and no software check in either can see it.
2. **The connection key is a uniqueness tripwire at configuration load. It is not the instance's identity.** ADR 0007 requires an instance identifier that is configuration-assigned and "not derived from a hostname, connection string or deployment name", and this ADR does not change that: identity stays the assigned identifier. The key (host, resolved addresses, port, and namespace where one applies) is only used to refuse two identifiers that collide. **The broker kind is not part of the key**, so one instance reached over CIA by one identifier and over XWB by another collides instead of passing as two. Configuration load fails when:
   - two tenants name the same instance, or two instance identifiers have the same key, including by DNS alias as the resolver answers at load time;
   - a tenant has no active instance, or more than one;
   - an enabled connection belongs to no tenant;
   - the topology cannot be established at all (see decision 8).

   Resolved addresses can change under round-robin DNS without the instance changing, and a proxy, a load balancer or a second listener in front of one instance gives two keys for one instance. The key catches the careless case. It proves nothing about identity, and decision 3 is a partial backstop, not a proof.
3. **A runtime site check is required, and it is weaker than "attestation".** At sign-on of a service account the app compares what the connection reports about its site against what is configured for the tenant. A mismatch refuses the connection and records a security event. **An empty or unusable answer is a mismatch, not a skip.** Without the check, two tenants whose endpoints are swapped (A to B's, B to A's) pass every load-time check.
   - The stock path is `RpmsRpc::Site.current`, which wraps `BEHOSICX SITEINFO`. The RPC returns `^XMB("NETNAME")`, the station number and related fields of the signed-on `DUZ(2)`'s institution record, `DUZ(2)` itself, and `DUZ("AG")`. That is a **site key held in the database**. We write no M.
   - **It needs a gem change first** (gem change 7).
   - **What it cannot do.** A copy of an instance reports the same site key: a sandbox restored from production, or the YottaDB side of an IRIS to YottaDB cutover. So it catches a swap between two different sites and nothing between copies of one site. Separating copies needs something that differs per instance, and no stock source for that has been identified. **Keeping a sandbox, a retired instance and the live one apart is a deployment control, not something the software enforces.** The cutover and sandbox procedures must say so, and decision 7's dual-run rule rests on it.
   - **Not established from code:** whether `DUZ(2)` is set on a service-account sign-on. If it is not, SITEINFO's fields are mostly empty. That is why an empty answer must refuse: otherwise the check passes in every mock and compares nothing on a live build.
4. **A system token runs on its tenant's connection as a named service account.** The client's registration gives the tenant, the tenant gives the instance, and the session is the **backend client's** service account on that instance (ADR 0011 section 6: one account per backend client). With no account configured the request gets 503 and sends no RPC, which is what a system token gets today for want of any connection. It never runs on a clinician's session and, once the unwrapped sites are closed (decision 6), never reaches another tenant's instance.
   - **Promise, not enforced:** that the account is provisioned on that instance only, and that its credentials come from host secrets. The app cannot know the same access and verify pair was not provisioned on a second instance. Provisioning is a site task.
   - The RPMS keys of each account are the ceiling on what its own client can do; scopes only narrow them. A tenant's total exposure is the union across its clients' accounts.
   - Jobs follow ADR 0012 rule 8: a job stores its principal, scopes, request id and tenant at enqueue, and runs on that tenant's connection under a service account, acting on behalf of that principal. It fails when no account is configured. It never defaults to a process client, because a serving process has none (decision 8); this amends ADR 0011 section 1, which says `RpmsRpc.client` stays for jobs. A job runs inside a serving process under the in-process adapter the dummy app uses (`test/dummy/config/application.rb:8` loads Active Job with no adapter configured) or in a worker process that is a serving process under decision 8, so it follows the same rule. No job on main calls `RpmsRpc` today, so this binds future jobs only.
   - Blast radius: a stolen service-account credential is a stolen account on one tenant's instance and no other. Least-privilege keys and rotation are the controls; neither is new to this ADR.
5. **Divisions never separate tenants.** A second division on an instance belongs to the same tenant. Of ADR 0007's division machinery:
   - **to be kept, once built**, as mis-map detection (rpms-rpc#293, open and unbuilt; nothing enumerates divisions today): enumerate divisions at startup; fail closed on a division that maps to no tenant; capture the signed-on `DUZ(2)` and refuse one not allowlisted for the token's tenant. Until it exists, this is a promise, and decision 3 is the only runtime check;
   - **retired**: `(tenant, instance, division)` as a configuration triple that partitions tenants. Configuration is `(tenant, instance)`, and the division allowlist is an attribute of the tenant.
6. **The runtime property: no tenant request reads through an unscoped or wrong-identity client.** In any process that serves a tenant, a read that does not run inside a scope holding that tenant's client for that request's principal is refused, and a send on a client whose identity is not the expected one is refused. A boot check alone does not give this: it says nothing about which client a request used. The per-user connections already give it for a signed-in browser user and refuse an API request. This ADR makes it a property that stays true for every request and every process: not undone by a later setter, not inherited by a child, compared at send time, audited, and extended to a system token's own identity. The mechanism is ADR 0011 as amended. This ADR requires these properties of it, and the gem changes that give them are listed below.
   - **a. No process-global client in a serving process, after boot as well as at boot.** The engine refuses to boot a serving process that already has a global client, and no longer installs one for the live suite (`engine.rb:76`). A boot check is a snapshot, so a client configured after boot must also fail: with the property in force, an unscoped call raises `NotConfiguredError` whatever was configured later, and the setter and `RpmsRpc.mock!` refuse. A non-serving process reaches a global only through an explicit opt-in that request paths never call. *Needs gem change 1.*
   - **b. The scope belongs to one request and is not inherited.** The scope is opened at the request boundary from the tenant's pool for the request's principal (a service account for a `system/` token), and is cleared on every exit from the request, including an exception. A fiber, thread or external enumerator started inside the scope does **not** inherit it: a child that needs RPMS takes an explicit client or gets `NotConfiguredError`. Inheritance lets a long-lived child keep the first request's client after the request ends; the pool's own keeper thread (`SessionPool#start_keeper!`, `session_pool.rb:227-231`) is the concrete case. *Needs gem change 2.* At the pin this property is **false**: a probe against the pinned gem on Ruby 3.4.7, 3.4.9, 4.0.2 and 4.0.6 found that `Fiber.new`, `Thread.new`, `Enumerator#next`, `Enumerator::Lazy` and a `Timeout` block all see the scope, and a thread started inside the scope still holds the client after the scope exits. The gem's own spec test asserts the inheritance, and three texts say it (see gem change 2).
   - **c. A send-time identity check, against an identity the scope carries.** Before an RPC is sent, the identity of the client that sends it must equal the identity the scope expects: the request's principal, or for a `system/` token the tenant's service-account DUZ for that backend client. A mismatch raises, sends nothing, and records a security event. A scope that carries **no expected identity refuses**; it neither records "unattributed" and sends nor skips, which is the shape in which a job on a thread pool would pass while broken. Checkout-time assertion alone is too early: the live defect was one connection changing identity between calls. The client-side comparison (`Client#duz`, present on both broker kinds at the pin) needs no gem change to catch the defect that happened, a second `authenticate` on the same client; the place it runs on gem-module calls is the call path of gem change 4, with the identity carried by gem change 5. It trusts the client's own memory, so a raw sign-on RPC that re-binds the M process without touching that memory must also be refused (gem change 3). The server-side read of the signed-on user costs one RPC per call and is not chosen. *Needs gem changes 3 to 6.*
     - **The sign-on scope is the one exception, and it is stated, not implied.** `AuthenticationService#authenticate_on_own_connection` (`authentication_service.rb:45-62`) opens `RpmsRpc.with_client` on a fresh, unauthenticated client. Inside that scope there is no DUZ to expect until `authenticate` returns, and the reads that follow in the same scope (user class, user info, idle limit, held keys, option access: `resolve_signon`, `authentication_service.rb:77-110`) are ordinary RPCs, not authentication RPCs, so the exemption for the auth RPC names does not cover them. A scope opened for sign-on therefore starts with the identity **to be established**; when `authenticate` succeeds and sets the client's DUZ, that DUZ becomes the scope's expected identity for every call after it, and a failed sign-on leaves the scope refusing. Only the engine's sign-on code can open a scope in this state, and no gateway can. Every other scope with no expected identity refuses. *Needs gem change 5.*
   - **d. Wrong-tenant scope is refused, not just missing scope.** A call inside tenant B's scope while serving tenant A's token must fail with a tenant-mismatch reason. A missing scope raising is the easy case and does not cover a scope opened for the wrong tenant. *Needs gem change 5 (the scope carries the expected tenant) and the comparison of gem change 4.*
   - **e. One door, with its real reach.** The door is the code that opens and holds a scope: `RpmsSessions` and `RpmsUserScope` (built in the per-user connections work), `AuthenticationService` and `SessionsController` for sign-on and adoption, the gateways in `app/gateways` for the calls themselves, the console, and the engine's boot path. A test fails when a **client-resolving reference** appears outside that layer. A client-resolving reference is `RpmsRpc.client`, `RpmsRpc.configuration.client`, `RpmsRpc.fhir_client`, `RpmsRpc.configure`, `RpmsRpc.mock!`, `RpmsRpc.with_client`, `RpmsRpc::SessionPool`, or a call on a gem API module (`RpmsRpc::<Module>.<method>`). **Allowed everywhere, by rule:** error and exception classes named in `rescue` and `rescue_from` (`RpmsRpc::Client::ConnectionError`, `NotConfiguredError`, `SessionPool::PoolExhaustedError`, `RpmsRpc::Error`), and pure parsers with no client (`RpmsRpc::FilemanDateParser`). Any other exemption is a path named in the test with its reason beside it, and there are no wildcard exemptions. The scan is by reference, not by a grep for `Module.method`.
     - **The test is expected to be red on main today, on real leaks, and each one is the point.** Controllers and models that resolve the client themselves: `RpmsRpc::Patient.brief_header` called from `registration/patients_controller.rb:47` and `:145` and `scheduling/patient_appointments_controller.rb:16`; `RpmsRpc.client` in `backend_registry.rb:140`; `RpmsRpc.configuration.client` in `web_controller.rb:113`; `RpmsRpc.fhir_client` in `patient_repository.rb:64` and `:76`; and the `MockClient` type check in `fhir/capability_statement.rb:154`. It goes green when each is moved behind a gateway or exempted by name with a reason. It must not be red on code that is correct: error-class rescues and the sign-on and scope plumbing are inside the rule, so the test does not fail on them.
     - **Its reach is leaks out of the layer** into controllers, services and models. **It cannot see a gateway that runs outside a scope**, because every gateway lives inside the permitted layer, so a new gateway in the injected style does not trip it; the property "every gateway runs inside a scope or raises" is carried by 6a, 6b and the runtime tests below, which drive every gateway constant.
7. **Who may change the mapping, and what a move is.**
   - The tenant-to-instance mapping is operator-held deployment configuration. **Software** can detect a change; it cannot know who edited it or whether it was reviewed. At boot the app compares the loaded mapping with the one it last recorded, and any difference writes a security event with the old and new value. The change takes effect at boot only. **Where "last recorded" lives is stated, and the first-boot case fails closed:** the record is a row in the application database. A serving process (decision 8) that finds the mapping configured and **no recorded mapping** refuses to serve until an operator records it with an explicit command, so a fresh database, a restore or a deleted row cannot silently accept whatever is loaded. This holds in every environment. The record command and the database tasks that create the table must be run as non-serving processes, declared by the caller (decision 8), which is why the first deployment can create the table that holds the record. A person who controls both the database and the config source can still change both; that is a process control.
   - Review by someone other than the author, and protection of the config source, are **process controls** of the deployment (for example branch protection). They are required, and they are not something an acceptance test can prove.
   - A cutover (for example IRIS to YottaDB) is a change of a tenant's active instance, not a second tenant. The tenant keeps its record, its `organization_id` and its stamped rows; the old instance is marked retired in the same change, so a tenant never has two active instances. During dual-run the retired instance is read-only and is not counted against decision 2's uniqueness test while marked retired. The site check in decision 3 cannot tell the retired copy from the new instance; the cutover procedure, not the software, keeps them apart.
8. **Boot does not fail open, in any environment, in a serving process.** Topology validation runs regardless of whether a client was already set and regardless of a blank host. In a serving process, a pre-injected process-global client, or a blank host with tenants configured, is a boot failure in every environment, development included. There is no carve-out for the spike mock and none for the test suite; the live suite's global client (`engine.rb:76`) moves behind a scope too.
   - **Process classes: a choice of declaration over detection, with the reason.** A **serving process** answers requests or runs jobs for tenants: the application server (Puma, Falcon, `rails server`), a job worker, and the in-process job adapter inside either. A **non-serving process** is `rails console`, `rails runner`, rake tasks (including `db:create`, `db:migrate`, `db:prepare` and the record-mapping command of decision 7), and asset tasks. The engine **could** classify a process itself: it already reads Puma's configuration at boot (`rpms_sessions.rb:93-105`) and already reads `Rake.application` in an initializer (`engine.rb:126-130`), so a rake process could be recognised there from `Rake.application.top_level_tasks`. This ADR instead has the class **declared by whoever starts the process, with an undeclared process treated as serving**. The declaration is `LAKERAVEN_EHR_PROCESS=maintenance`, set by the caller: the operator or deploy script for console, runner, rake and the record command, and CI for its `rails db:create db:migrate` and `db:schema:load` steps (`ci.yml:52`, `:104`, `:161`). **Why declaration:** a detector has to name every maintenance entry point (console, runner, the database tasks, asset tasks, every custom task and `bin/` script) and every serving one (a rake-launched job worker is a `rake` process like a migration), and it must default to serving for anything it does not recognise; each maintenance step an operator adds, including the record command, would then need an engine change, and a task whose name looks like maintenance but starts a worker would pass as non-serving. A declaration costs the operator one variable and cannot be forged by a task. Both choices refuse on omission. The name is decided here and confirmed in the implementation issue, and **if the deployment later prefers detection, the properties of this decision are unchanged and only the classifier changes.**
   - **One software check backs the declaration where the engine can already see the server.** A process that declares itself non-serving while Puma is running as the server (`::Puma.cli_config` set, the signal `assert_single_process!` already reads) is refused at boot. That closes the worst case of a forgotten or mistaken flag on the application server, and nothing else: Falcon, a job worker and any other server are not covered, and are the deployment control's residue.
   - **Tasks cannot declare themselves.** The application has fully booted, boot check included, before any rake task body runs: the database tasks depend on `load_config`, which depends on `environment`, and the engine's check runs in `config.after_initialize`. An environment variable set inside a task body is set too late, so this ADR does not claim the tasks set it. An initializer-time detector (above) is the alternative to a caller declaration. A rake-launched job worker is a serving process and must not be declared maintenance.
   - **The test runner is serving by default** (`rails test` is not among the declared steps and boots the application in-process, `test_helper.rb:6`). The test environment therefore configures **zero tenants at boot** and boots with no global client; each test configures its tenants and scope through the harness below, so the load-time checks of decision 2 are exercised by the subprocess boot tests, not in-process.
   - **What each class may do.** A serving process has no process-global client and runs the strict property of decision 6a. It also runs one Puma process (ADR 0011's sticky-session note stays a deploy decision, and `assert_single_process!` enforces it for Puma). A non-serving process may reach the global only through the explicit opt-in, and signs on as a named identity of its own, which is ADR 0011 section 1's text for the console and rake tasks. ADR 0011 section 1 is amended: `RpmsRpc.client` no longer stays for jobs.
   - **Zero tenants is not a failure.** A serving process with no tenant configured and no host named still boots and logs that no RPMS backend is configured, as `README.md:62` and the `engine.rb:53-57` comment say; no tenant request can reach RPMS. What fails is the combination of tenants configured with a blank host, a pre-injected global client, or an unrecorded mapping (decision 7). `README.md:62` and `:63` (the sentence that the engine "leaves a configured client alone") and the `engine.rb:53-57` comment change to say so, and `engine.rb:61` (the early return when a client is already set) and `engine.rb:76` (the live suite's global) are removed or moved behind a scope.
   - **The development spike mock** (`test/dummy/config/initializers/zz_spike_mock_rpc.rb:20`) moves behind the same scope: it opens a scope around each request for the mock client and configures no global.
   - **The test suite's global** (`RpmsRpc.mock!(&BASELINE_MOCK_SEEDS)`, `test_helper.rb:231`, re-installed before every example by `GlobalStoreIsolation`, `global_store_isolation.rb:21`) moves behind a scope as well, and `use_broker` (`test_helper.rb:309-314`) with it. This is not a small change: **every** request in the suite, including bearer-token tests that never sign on to RPMS (for example `organization_boundary_test.rb`), then needs a scoped client, and a request with none gets the sign-in page under ADR 0011 section 5. **The harness has starting points on main** and is not a blank design: `GlobalStoreIsolation` already resets `RpmsSessions` before every example (`global_store_isolation.rb:15`), and `per_user_rpms_connection_test.rb` defines `UserClient < RpmsRpc::CiaClient` (connect, `connected?`, `disconnect`, an `authenticate` that sets the DUZ, a `call_rpc_raw` framed as the CIA broker frames it) and adopts it into the pool. What is missing is a per-test adoption of a mock client under each test principal's session or token key, a service-account mock per test tenant, and a `UserClient` that is a `MockClient` so the call path fires on it (gem change 6). The acceptance tests below depend on that harness, which belongs to the implementation issue.

   A boot check and an initializer that sorts last (`zz_` runs after any validation initializer) are not enough on their own; the acceptance test runs the real boot path in a subprocess.
9. **Every call is audited, and the identity check runs on every call, below the public entry points.** Every system read records the tenant, the instance, the service-account DUZ, the client application and the request id, **together with the fields `AuditedBroker` records today**: the acting agent's attributes, the network address and the facility (`AuditContext`, `audited_broker.rb:98-111`). It records them whichever gateway or module made the call and whichever public client method carried it. This is a property of the gem's call path, not of a wrapper the engine puts around the client: `AuditedBroker` sits on 16 `RpcSupport.broker` sites, its header says gem-module calls bypass it, and a wrapper that does not forward the whole client surface degrades silently (its allowlist forwards only `connected?` and `hostname`, `audited_broker.rb:78`; it hides `with_context`, `synchronize_wire`, `call_rpc_lines`, `call_rpc_global_array`, `duz` and `authenticated?` from callers that guard them with `respond_to?`, which re-serializes users through the process-wide wire lock and removes the identity check's input). The properties required, and the gem changes that give them (4, 5 and 6):
   - **The record and the identity comparison happen below every public entry point that sends an RPC**, including the raw ones, on every transport, and on the mock the tests use. A hook that only wraps `call_rpc` is a second door.
   - **The refusal `AuditedBroker` gives today is kept.** The 16 audited sites cannot reach `call_rpc_raw`, `read_response`, `authenticate` or `connect` today; once the engine holds the raw client, those must still be unreachable from a gateway. The one caller that must reach `authenticate` and the post-sign-on reads is the sign-on code under decision 6c's exception, and it is not a gateway.
   - **Fail closed after the call** (the result is withheld if the row cannot be written), **a failed call is recorded with its outcome** and the original exception preserved, and the row is **written detached from any open transaction**. These are `AuditedBroker`'s semantics today and are the contract of whatever replaces it.
   - **The expected identity and the audit fields come from the scope** (decision 6c), set when it opens; with none, the call is refused, except in the sign-on scope.
   - **Promise, not enforced, until built:** that every read is recorded. Until the call path exists, audit covers the 16 `RpcSupport.broker` sites only. Security events: a refused attempt to reach another tenant, a site-check mismatch, an identity mismatch at send time, and every mapping change.
10. **What stays from ADR 0007 and ADR 0011.** The tenant record with `organization_id` as an immutable foreign key, the session-bound client of ADR 0011, and `tenant_id` stamping on locally held rows, cache keys, jobs and audit rows. Stamping is now needed before a second tenant shares a **process or database**, not before one shares an instance, because one process or database can serve several tenants even when no RPMS instance is shared. The `organization_id` string column is backfilled into the tenant record by ADR 0008 step 1 if that ADR lands, and by the tenant record's own migration otherwise; the request context's `organization` (ADR 0012) resolves to the tenant through that foreign key.
11. **The interim guard is replaced by decision 2.** It is removed when the scoped client is live for system tokens, as ADR 0007 already says. A sandbox instance is a tenant with its own instance and is not blocked by the guard once it is gone.

## What the software enforces and what it promises

| Property | Enforced by software | Promise or process control |
|---|---|---|
| Two tenants never name the same instance | Load-time key check, within one deployment | Across deployments; round-robin DNS and proxies; the resolver's answer at one moment |
| A swap between different sites | Site check at sign-on (once gem change 7 lands) | Copies of one site (sandbox, retired, live) |
| A signed-in user's request runs as that user | The per-user scope already on main; a request with none gets 503 | That nothing re-opens a global (see the next rows) |
| A system read runs as that backend client's account | 503 with no RPC when no connection exists, today; the service-account scope and the send-time identity check against the identity the scope carries, **after gem changes 3 to 6** | That the account exists on that instance only; host-secret provisioning; a raw auth RPC until gem change 3 |
| No unscoped or wrong-tenant read | Boot refuses a global client in a serving process, and an unscoped call raises while none is configured; **after gem changes 1 and 2**, a later setter refuses and the scope is not inherited; **after gem changes 4 to 6 and 5**, a call inside the wrong scope raises | Until those land, boot is a snapshot and children inherit the scope; the unwrapped sites are closed only when converted and tested (roughly 140); **declaring a process non-serving is a deployment control** (one case, a declared non-serving Puma server, is refused) |
| Mapping changes are visible | Security event at boot; a first boot with no record refuses a serving process | Review of the change; control of the config source and database; the caller declaring the database tasks and the record command non-serving |
| Divisions map to one tenant | Nothing, until rpms-rpc#293 | The division allowlist, today |
| Every system read is audited | The gem call path (gem changes 4 to 6), once built | All reads outside the 16 `RpcSupport.broker` sites, until then |

## Required gem changes

Each is owned in rpms-rpc, **specified and gated in its own rpms-rpc issue** (a failing spec first, written by a seat other than the builder). This ADR names the property each must give and the finding it answers; it does not fix the design. The per-user connections work did not make any of them obsolete: it changed the engine, and the gem files these changes touch are unchanged between the earlier pin and 6723a7f except for the session pool.

1. **Strict mode, so a configured global is never a fallback.** Property: with strict mode on, `RpmsRpc.client` never falls back to `configuration.client`, `Configuration#client=` (the setter) and `RpmsRpc.mock!` refuse, and the global is reachable only through an explicit opt-in. `configure` itself stays callable for its other settings. The engine turns it on when it boots a serving process. rpms-rpc ADR 0006 made the scoped design acceptable only on these terms, and the scope shipped without them. *Answers:* the fallback at `core.rb:57` and the open setter at `core.rb:33` leave a boot check as a snapshot.
2. **A scope that children do not inherit.** Property: a `Thread.new`, `Fiber.new` or external `Enumerator#next` started inside a scope raises `NotConfiguredError` when it calls RPMS, the scope is cleared on every exit including an exception, and an external enumerator used inside a scope raising is the stated cost (nothing in this repo's `app` or `lib` uses one). Also: ADR 0011's amendment sentence, rpms-rpc ADR 0006's "any `Thread.new` inside a scope loses it", and the `core.rb:67-69` comment are edited to say one thing, and the gem spec `scoped_client_test.rb` (`test_threads_and_fibers_started_in_a_scope_see_it_and_others_do_not`) asserts inheritance today. **That spec test is reviewer-owned: the spec author rewrites it to assert the opposite and the builder makes it pass without editing it.** *Answers:* the probe result in decision 6b.
3. **A runtime refusal of identity-changing RPCs from outside the client's own sign-on.** Property: the client refuses, at runtime, an RPC that binds or rebinds the M process's user or division when it is sent through **any** public entry point (`call_rpc`, `call_rpc_raw`, `call_rpc_lines`, `call_rpc_global_array`), except from the client's own sign-on, and the exemption cannot be reached by a gateway. The refused list must be named in the issue, and must include the RPCs the gem itself sends to sign on (`XUS AV CODE`, `XUS SIGNON SETUP`, `CIANBRPC AUTH`), the division switch that rebinds `DUZ(2)` without touching the client's remembered DUZ (`XUS DIVISION SET`), and the BGU names `forbidden_auth_rpcs_test.rb` scans for today. **`XWB CREATE CONTEXT` is not on the list.** It binds an option, not the user or division; `create_context` requires an already authenticated client (`client.rb:515`), and `with_context` sends it on every scoped call on XWB (`context_scope.rb:70-86`; 15 call sites in 7 API modules), so refusing it outside sign-on would break every scoped call. Today the gem's own sign-on goes through `call_rpc` and `call_rpc_raw` (`client.rb:355`, `:382`, `:521`; `cia_client.rb:231`), so a refusal defined on `call_rpc` alone is green while `call_rpc_raw("XUS AV CODE")` stays open. *Answers:* the raw sign-on path and the unrefused `XUS DIVISION SET`.
4. **A call path that records and compares below every public entry point.** Property: the audit record and the identity comparison of decisions 6c and 9 run below `call_rpc`, `call_rpc_raw`, `call_rpc_lines` and `call_rpc_global_array` on every transport (CIA funnels them through one exchange; XWB and BMX have separate wire blocks), with `AuditedBroker`'s refusal of `call_rpc_raw`, `read_response`, `authenticate` and `connect` kept for gateway callers, and with the fail-closed, outcome-recording and detached-write semantics of decision 9 and the audit fields it names. The full client surface the gem modules call keeps working: `with_context`, `synchronize_wire`, `call_rpc_lines`, `call_rpc_global_array`, `duz`, `authenticated?`, `poll`, `disconnect`. *Answers:* the wrapper's two-name allowlist.
5. **The scope carries the expected identity and the audit context.** Property: opening a scope takes the expected DUZ, the expected tenant and the audit fields (tenant, instance, client application, request id) as its own state, and the call path of gem change 4 reads them from the scope. A scope with no expected identity refuses every call, **except a scope opened in the sign-on state** (decision 6c): it expects an identity "to be established" and takes the DUZ that `authenticate` sets on its client. An in-process job adapter or a thread pool outside a request therefore refuses and is never recorded as unattributed and sent. *Answers:* the hook's lack of any expected identity, and the sign-on sequence that opens a scope before a DUZ exists.
6. **`MockClient` has the identity and lifecycle surface of the real clients, and calls the same call path.** Property: the mock models `authenticate`, `authenticated?`, `set_authenticated`, `clear_authenticated`, `duz`, `connected?`, `hostname`, `poll` and `disconnect`, stamps each received call with the DUZ it was signed on as at call time, and invokes the call path of gem change 4, so a test on the mock exercises the same refusal and audit as live. Without this, acceptance tests 1, 2, 10 and 11 cannot run, or pass vacuously with the mock never signed on as anyone and never firing the call path (`api/authentication.rb:72` and `:336` skip identity on the mock through `respond_to?`). If the gem will not take it, the engine's test harness supplies an equivalent fake, building on `UserClient` in `per_user_rpms_connection_test.rb`, and the issue says so. *Answers:* the pinned mock's missing identity surface.
7. **A site mapping that exposes the fields the site check compares, under their true names.** Property: the gem's site mapping exposes the station number (today named `abbreviation`) and `DUZ("AG")` (today dropped), and `Site.current` accepts the service account's DUZ. *Answers:* the site check in decision 3.

The engine changes beyond the gateways, owned in lakeraven-ehr: the process declaration, the Puma backstop and boot rules of decision 8, `README.md:62-63` and the `engine.rb:53-57` comment, the removal of the `engine.rb:61` early return and the `engine.rb:76` global, the conversion or enclosure of the roughly 140 sites and the leaks listed under decision 6e, the sign-on scope's use of the sign-on state, and the per-test harness for the suite.

## Acceptance tests

Each test names how it could pass while its property is broken, the assertion that closes that, and the gem change it needs, so it cannot pass vacuously. All use two tenants, each with its own mock instance, whose patients have **overlapping DFNs and visibly different fields** (name, date of birth), so the answer's origin is visible from the body. A test that needs a gem change is red until that change lands, which is how it gates the change. The mock records, for every call it handles, the DUZ the **executing client object** was signed on as at call time (gem change 6).

- **Reused thread, two users, default-provider gateway.** One reused thread serves two sequential requests as different users, each through a gateway written as `via: default_provider`. Assert that the DUZ the mock stamped on each call equals that request's user. *Passes while broken if* the recorded DUZ is read from the request and not from the client that executed the call, in which case it matches trivially; so the assertion reads the mock's stamp. It also fails if the scope is left on the thread or the gateway reads a leftover client. *Needs gem changes 2 and 6.*
- **A cannot read B, one call per gateway constant.** `RpmsRpc.configuration.client` is nil for the whole test, through the per-test harness of decision 8. A's token reads a patient that exists on both, through **one call per gateway constant** in `app/gateways`, enumerated from the constants, not through one route. Assert on the identity of the client that served each call (its pool key and DUZ), not on a status code or body alone. This enumerates gateways, not the roughly 140 call paths, which have different arguments and cannot be driven generically: the untested methods are the ones behind `via:` and are carried by gem changes 1, 2 and 4. *Passes while broken if* only one route per gateway is converted, if the fixture that is A's instance is also installed as the global (the current helper does exactly that), if the two instances look alike, or if the mock never invokes the call path. *Needs gem changes 4 and 6.*
- **Wrong-tenant scope is refused for that reason.** Inside a real request carrying A's token, run a call inside B's scope. Assert it raises, sends nothing, and that the security event's reason is a tenant mismatch. *Passes while broken if* the test opens B's scope with `RpmsRpc.with_client` outside any request, because the refusal then comes from a missing principal and the test is green for the wrong reason. *Needs gem changes 4 and 5.*
- **Strict property holds after boot, in a subprocess.** Boot a serving process cleanly, then set a client through the setter and call `RpmsRpc.mock!`. Assert both refuse and that an unscoped call still raises `NotConfiguredError`. *Passes while broken if* only the boot check is tested, which is the snapshot the gem's fallback defeats; or if it runs in the test process, which is serving by default but runs with the scope harness, so it must be a subprocess. *Needs gem change 1.*
- **One door, with its real reach.** The test of decision 6e, with the layer, the allowed-by-rule references and the named exemptions as stated there. It is **red on main on the leaks listed under decision 6e and green on the sign-on and scope plumbing and the error-class rescues**; a run that is red on any of those is a defect in the test, not a leak. It says nothing about a gateway that runs outside a scope. *Passes while broken if* it is read as covering gateways, which it cannot; the runtime tests carry that property. A grep for `Module.method` would miss both `via:` calls and the `RpmsRpc.client`, `configure` and `mock!` forms, so the scan is by reference.
- **Child does not inherit.** Start a thread, a fiber and an external enumerator (`.next`) inside a scope and assert each raises `NotConfiguredError` when it calls RPMS, that after an exception in the request the scope is cleared, and that `SessionPool#start_keeper!` first called inside a request scope does not capture that request's client. *Passes while broken if* the scope is copied to children, survives an exception, or the keeper is started before the test, so the test starts it inside the scope. It is red at the pin. *Needs gem change 2.*
- **One endpoint fails load.** Run it against the real boot path for the cases a test can control: the same endpoint, `localhost` against `127.0.0.1` for one listener (and `::1` where the runner has an IPv6 listener; the test says it skipped that case when it did not), a second port on the same host and namespace, and two identifiers with one key reached over CIA and over XWB. A collision is **any shared (address, port) pair**, not equality of the two resolved address sets. The test **does not** claim to exercise DNS aliases or round-robin resolution; those are a deployment control and the ADR says so. *Passes while broken if* broker kind is in the key, or the key compares address sets for equality, so that `localhost` (which resolves to `127.0.0.1` and `::1`) and `127.0.0.1` count as two keys.
- **A swap between different sites is refused at sign-on**, with fixtures whose site answers differ. **A fixture whose answer is entirely empty is refused, not skipped.** The test does not claim to catch copies of one site. *Needs gem change 7.*
- **No account means 503, no RPC and no fallback.** Run it with a clinician signed in on the same process and with `RpmsRpc.configuration.client` nil. Assert the refusal reason (no account configured, not a connection error, since the broker wrapper also answers 503 for any connection failure) and that no RPC was sent on any pooled client. A job for a tenant with no account fails and does not run.
- **Identity mismatch at send time, within one lease.** Make two calls inside one scope on one checked-out client and, between them, run a second `authenticate` on that client as a different user. The second call raises before any RPC is sent. *Passes while broken if* the test changes the DUZ before checkout, because the existing checkout assertion then satisfies it with no send-time check. A second case sends an identity-changing RPC (`XUS AV CODE`, and `XUS DIVISION SET`) through **each** public entry point, `call_rpc`, `call_rpc_raw`, `call_rpc_lines` and `call_rpc_global_array`, from a gateway-held client and asserts the client refuses it at runtime, not through a source scan. A third case asserts the client's own sign-on still works, **including the whole sign-on sequence**: after `authenticate`, the user-class, user-info, idle-limit, held-key and option-access reads of `resolve_signon` all succeed inside the same scope and are recorded under the DUZ that `authenticate` set (see the sign-on test below). *Passes while broken if* only `call_rpc` is tried, or the third case exercises the auth RPCs and not the reads. *Needs gem changes 3, 5 and 6.*
- **Sign-on stays green under the refusal rule.** Sign in through `AuthenticationService` with the refusal and the call path in force. Assert the sign-on succeeds end to end and that every read after `authenticate` is recorded under the DUZ `authenticate` set; that a scope opened in the sign-on state **from a gateway** cannot be created; that a sign-on that fails leaves the scope refusing every further call; and that every other scope with no expected identity refuses. *Passes while broken if* the exemption is implemented as a general "no identity means allow", which the last two assertions catch. *Needs gem change 5.*
- **The call path records, refuses and does not change behaviour.** Enumerate the client methods the gem modules call. For a scoped call, assert an audit row is recorded (with the scope's audit fields published, including the agent attributes, network address and facility that `AuditedBroker` records today), that `with_context` runs and sends `XWB CREATE CONTEXT` on an XWB client without being refused, that the per-client wire lock is taken and `MODULE_WIRE_LOCK` is not, that `call_rpc_lines` and `call_rpc_global_array` reach their own entry points, that `call_rpc_raw`, `read_response`, `authenticate` and `connect` are refused for a gateway caller, and that a call with no expected identity (outside the sign-on state) refuses and records nothing as unattributed. Run it on the mock **and** on the live container; on the mock it must be shown to invoke the call path. *Passes while broken if* it runs only on a mock that never invokes the call path. *Needs gem changes 4, 5 and 6.*
- **Boot does not fail open.** Boot the real application in a **subprocess**, once per case, with development as the environment, and its **own `DATABASE_URL`** (CI creates only the test database). A serving process exits non-zero for each of: a pre-injected global client (injected by an initializer the test writes, since the spike mock no longer installs one), a blank host with tenants configured, and a mapping configured with no recorded mapping. The same boot with zero tenants and no host **succeeds** and logs that no RPMS backend is configured. A process declared non-serving by the caller (`LAKERAVEN_EHR_PROCESS=maintenance`) boots with the mapping unrecorded, runs `db:create db:migrate`, and runs the record command; an undeclared process is treated as serving; and a process declared non-serving under Puma as the server is refused. *Passes while broken if* the validator is called in-process with injected settings; that does not prove initializer order.
- **A changed mapping is detected.** Boot against a recorded mapping that differs from the loaded one and assert the security event. Review of the change is a process control and is not tested here.
- **The skipped boundary test is replaced.** `organization_boundary_test.rb:47` is skipped and asserts a status code, the shape this ADR says is insufficient. It is deleted when the identity-based test above lands, not left beside it.
- **Break each check on purpose** and confirm its test goes red. An unverified gate is a comfort, not a control.

## Consequences

- A tenant record must exist before any of this is built (ADR 0007), and the configuration needs a place for the tenant-to-instance mapping and a place for the last recorded mapping. The mapping is operator-held deployment configuration, never a client-registration field.
- ADR 0007's "several entities on one instance" branch becomes dead design. Its table of divergences loses one row.
- **ADR 0007's requirement that the model express a governance domain narrower than the covered entity is not met by this ADR.** An organization serving several governance domains on one instance cannot be expressed as several tenants under decision 1. The requirement is dropped here, deliberately, and declared in Amends. If a domain narrower than the instance is needed, it is an attribute of the request context inside one tenant, not a new tenancy boundary (ADR 0010 section 5 reserves "scope" for the OAuth scopes and says tenancy between organizations is ADR 0007's boundary, not a scope), and a design for it is outside this ADR.
- A sandbox or test instance of an entity is a separate tenant. Any state shared between them is cross-tenant state and is treated as such.
- Onboarding a tenant includes provisioning a service account for each backend client and one for its jobs. That is a site task (L3), not an engineering one.
- A tenant on a retired instance during a cutover is allowed only for the dual-run period.
- The gem carries the seven changes above, each its own rpms-rpc issue. Several are reviewer-gated before they are built, and the spec test of gem change 2 belongs to the spec author.
- Declaring a process non-serving is a deployment control, backed by one software check for a Puma server. A deployment that forgets the flag on a database task gets a refusal, and one that sets it on a serving process other than Puma loses the guard with no software signal.

## Alternatives rejected

**Support shared instances with row scoping** (the path ADR 0007 left open). The boundary would be derived from RPMS data that carries no tenant, so a single missed filter is a disclosure. The maintainer's position makes the case unsupported rather than merely hard.

**Tenancy is the instance, with no tenant record.** A deployment label is not stable across moves and migrations, which is the reason ADR 0007 kept the tenant first-class. That reasoning still holds, and decision 7 relies on it. The tenant record stays; it is only constrained to one active instance.

**Rely on the boot check alone.** Rejected because it protects a configuration and says nothing about which client a request used; see decision 6.

**Thread an explicit session through every call.** It touches every public gem method (about 240 signatures) and every gateway, and a default argument such as `via: default_provider` resolves the ambient client when the argument is omitted, so an explicit parameter with a default is ambient authority written as a keyword. ADR 0011 as amended chose the scope for that reason; decision 6 keeps the scope and makes its guarantee testable.

**Wrap the scoped client in `AuditedBroker`.** The wrapper forwards only `connected?` and `hostname`, so the gem's guarded calls degrade silently and the identity check cannot read the client's DUZ; see decision 9.

**Let a system token ride a shared client.** Rejected by ADR 0011 section 6. A system token today gets no connection at all, which is safe and incomplete: it needs its own named account (decision 4).

## Not verified
