# ADR 0013: A tenant is exactly one RPMS instance, and an instance is never shared between tenants

**Status:** Proposed. The compliance premise has not been reviewed by counsel and needs that review before this can be Accepted.
**Date:** 2026-10-29
**Amends:** ADR 0007 (decision 1's "one instance may serve several entities", its rejection of "tenancy = the RPMS instance", the partitioning role of its division machinery, and its requirement that the model express a governance domain **narrower** than the covered entity; see Consequences) and, **if ADR 0008 lands** (it is open as #630), ADR 0008 (its "does not settle shared-instance tenants" and the trigger for its sequence step 4). This ADR decides nothing that depends on ADR 0008's text; see Merge order.
**Builds on:** ADR 0011 as amended (the request's client is a scope, not an argument; section 6, a system token runs as a named service account), ADR 0012 (the request context carries the tenant; see the note on rule 5 below), lakeraven-ehr#553.
**Requires edits to:** ADR 0011 (its amendment's sentence that the scope reaches "the fibers and threads it starts", and its section 1 sentence that `RpmsRpc.client` stays for jobs; see decisions 6b and 8), ADR 0012 (rule 5), and rpms-rpc ADR 0006 (its statement that a `Thread.new` inside a scope loses it, which is wrong at the pin until decision 6b's gem change lands).

## Context

ADR 0007 made the tenant the covered entity and let the covered entity and the RPMS instance diverge in both directions: one entity on several instances, and several entities on one instance. Because of the second case it required read scoping and `tenant_id` stamping as well as connection selection, and it rejected "tenancy = the instance" for being unable to represent two entities on one instance.

The maintainer's position is that an organization is one RPMS instance, and that two covered entities sharing an instance is not a topology to support. A read under one entity's authority would reach another entity's patients, and the maintainer treats that as a breach. This ADR does not interpret HIPAA or classify any occurrence; that is for counsel. It takes the position as its premise.

The consequence for design is that a shared instance is an error state to refuse, not a case to engineer around. **Refusing it at configuration load is necessary and not sufficient.** A boot check on a topology does nothing about the runtime identity of a request, so this ADR also states the runtime property the check protects (decision 6).

**The client mechanism is ADR 0011's, not this ADR's.** ADR 0011 as amended scopes the request's client with `RpmsRpc.with_client(client) { ... }` and removes every global client from serving processes (decision 8 defines the term), so a call made outside a scope finds no client and raises `RpmsRpc::NotConfiguredError`. At the pinned gem that sentence is a design intent, not yet behaviour: `RpmsRpc.client` still falls back to a configured global on every call, and the scope is inherited by children (decisions 6a and 6b). This ADR adds what a tenant boundary needs on top of that: the scope is opened for the right tenant, the guarantee is enforced and tested rather than assumed, and a scope cannot leak across requests or into children.

**ADR 0012 rule 5 and ADR 0011 now disagree, and this ADR flags it without editing 0012.** Rule 5 says the request context is an argument, "no thread-local, fiber-local or global holds it", and ADR 0012's table names `BrokerSession` as the explicit carrier of the client. Amended ADR 0011 carries the *client* in a scope. The two are reconcilable and the split this ADR uses is: **ADR 0011 governs how the client reaches the gem** (a scope); **ADR 0012 rule 5 governs the request context** (principal, scopes, tenant), which stays an explicit argument. The parenthetical in rule 5 that rejects the ambient approach "for the client", and the table row that calls `BrokerSession` an argument carrier, are stale under that split. They need an edit to ADR 0012, which is the maintainer's to make.

## What a system token does today

Measured on `main` at b7dcf2d unless a commit is named. Line references were refreshed against 497cecf. "The pin" means the rpms-rpc revision in this repo's `Gemfile.lock`, d59fe4a, which carries `RpmsRpc.with_client`.

- **Authorization identity.** `current_duz` is nil unless the token is a browser SSO token (`smart_authentication.rb:413-422`). That covers system tokens, and also any non-browser user or patient token.
- **Connection.** `RpcSupport.broker` wraps `BackendRegistry.current.client`, which is the process-global `RpmsRpc.client` (`rpc_support.rb:34-35`, `backend_registry.rb:140`). Nothing selects a connection by token or by application.
- **Most calls skip that wrapper.** Gateways mostly call `RpmsRpc::*` directly, so the audit wrapper is not on those paths, as ADR 0007 already records. `RpcSupport.broker` has 16 call sites, and the wrapper's own header (`audited_broker.rb:24-34`) says that closing the rest needs a client hook in the gem, not more wrappers in the engine.
- **Count.** Three populations reach the global client, and a one-line grep sees only the first.
  - **Direct module calls.** A grep for `RpmsRpc::<Module>.<method>` in `app` and `lib`, full-line comments excluded, gives 51 sites in 20 files at b7dcf2d and 52 in 20 files at 497cecf. Counting comment lines gives 85 lines in 32 files, which is the figure earlier drafts quoted as "in 32 files". Five of the sites are `RpmsRpc::FilemanDateParser`, a pure parser with no client, so **about 46** (47 at 497cecf) resolve the global client.
  - **Gateways that inject the module as a default.** The repo's standard gateway style is `def self.x(..., via: default_provider)` with `default_provider` returning an `RpmsRpc::*` module, then `via.method(...)`. The grep does not match it. About **58** such calls in **23** gateway files resolve the global client inside the gem exactly like the direct ones. That figure was measured at b7dcf2d and was not re-measured at 497cecf.
  - **Direct client reads.** `RpmsRpc.client` is read in `authentication_service.rb:116` and `:124` and `backend_registry.rb:140`.

  So the population is **roughly 105 sites** (46 + 58 + 3), spread over the 20 files that call modules directly and the 23 gateway files that inject them. The two sets overlap, so the file count is at most 43. The decisions below do not depend on the exact figure, and no acceptance test below is built from a grep.
- **So** the RPMS-side identity of a system read is whatever the global client is signed on as. ADR 0011 describes the CIA case as the last clinician to sign in. That case was not re-measured.
- **The binding.** `oauth_applications.organization_id` is a free-form string column. It is blank-checked at mint (`backend_services_controller.rb:62`) and read by the interim guard (`:285-290`). Nothing else reads it.
- **The interim guard** refuses to mint once a second distinct organization is registered. It compares `strip.downcase` strings, not endpoints, so two labels that point at one broker would not trip it.
- **Boot can already fail open.** `configure_rpms_broker!` returns without configuring anything if a client is already set (`engine.rb:61`), and boots with no backend on a blank host (`:63-66`); otherwise it configures a process-global client in every process (`:68-69`). At the pin a nil client raises `NotConfiguredError` on read, so "fail open" describes future routing, not today's behaviour.
- **The test suite and a development initializer install globals.** The test helper installs the mock client as the process-global with `RpmsRpc.mock!(&BASELINE_MOCK_SEEDS)` (`test_helper.rb:231`) and re-installs it before every example (`test_helper.rb:30-32`). `use_broker` (`test_helper.rb:309-314`) is a separate helper that swaps the global for a scripted fake in the registration and scheduling tests. A development-only spike initializer (`zz_spike_mock_rpc.rb:20`) calls `RpmsRpc.mock!` and installs a global mock client in a process that serves requests.

## Decision

1. **Tenant and instance are one to one.** Each tenant has exactly one *active* instance, and each instance is active for exactly one tenant. An entity that runs two live instances is two tenants. A move between instances is not that case; see decision 7. *Enforced:* within one deployment's configuration. *Promise:* across deployments. Two deployments (two application hosts) that point at one RPMS instance are invisible to both, and no software check in either can see it.
2. **The connection key is a uniqueness tripwire at configuration load. It is not the instance's identity.** ADR 0007 requires an instance identifier that is configuration-assigned and "not derived from a hostname, connection string or deployment name", and this ADR does not change that: identity stays the assigned identifier. The key (host, resolved addresses, port, and namespace where one applies) is only used to refuse two identifiers that collide. **The broker kind is not part of the key**, so one instance reached over CIA by one identifier and over XWB by another collides instead of passing as two. Configuration load fails when:
   - two tenants name the same instance, or two instance identifiers have the same key, including by DNS alias as the resolver answers at load time;
   - a tenant has no active instance, or more than one;
   - an enabled connection belongs to no tenant;
   - the topology cannot be established at all (see decision 8).

   Resolved addresses can change under round-robin DNS without the instance changing, and a proxy, a load balancer or a second listener in front of one instance gives two keys for one instance. The key catches the careless case. It proves nothing about identity, and decision 3 is a partial backstop, not a proof.
3. **A runtime site check is required, and it is weaker than "attestation".** At sign-on of a service account the app compares what the connection reports about its site against what is configured for the tenant. A mismatch refuses the connection and records a security event. **An empty or unusable answer is a mismatch, not a skip.** Without the check, two tenants whose endpoints are swapped (A to B's, B to A's) pass every load-time check.
   - The stock path is `RpmsRpc::Site.current`, which wraps `BEHOSICX SITEINFO`. The RPC returns `^XMB("NETNAME")`, the station number and related fields of the signed-on `DUZ(2)`'s institution record, `DUZ(2)` itself, and `DUZ("AG")`. That is a **site key held in the database**. We write no M.
   - **It needs a gem change first.** At the pin the gem's mapping exposes the station number under the name `abbreviation` and ignores the `DUZ("AG")` line entirely, and `Site.current(duz)` returns nil for a nil or non-positive DUZ, so it must be given the service account's DUZ. The mapping must expose the fields this check compares under their true names before the check can be built.
   - **What it cannot do.** A copy of an instance reports the same site key: a sandbox restored from production, or the YottaDB side of an IRIS to YottaDB cutover. So it catches a swap between two different sites and nothing between copies of one site. Separating copies needs something that differs per instance, and no stock source for that has been identified. **Keeping a sandbox, a retired instance and the live one apart is a deployment control, not something the software enforces.** The cutover and sandbox procedures must say so, and decision 7's dual-run rule rests on it.
   - **Not established from code:** whether `DUZ(2)` is set on a service-account sign-on. If it is not, SITEINFO's fields are mostly empty. That is why an empty answer must refuse: otherwise the check passes in every mock and compares nothing on a live build.
4. **A system token runs on its tenant's connection as a named service account.** The client's registration gives the tenant, the tenant gives the instance, and the session is the **backend client's** service account on that instance (ADR 0011 section 6: one account per backend client). With no account configured the request gets 503 and sends no RPC. It never runs on a clinician's session and, once the unwrapped sites are closed (decision 6), never reaches another tenant's instance.
   - **Promise, not enforced:** that the account is provisioned on that instance only, and that its credentials come from host secrets. The app cannot know the same access and verify pair was not provisioned on a second instance. Provisioning is a site task.
   - The RPMS keys of each account are the ceiling on what its own client can do; scopes only narrow them. A tenant's total exposure is the union across its clients' accounts.
   - Jobs follow ADR 0012 rule 8: a job stores its principal, scopes, request id and tenant at enqueue, and runs on that tenant's connection under a service account, acting on behalf of that principal. It fails when no account is configured. It never defaults to a process client, because a serving process has none (decision 8); this amends ADR 0011 section 1, which says `RpmsRpc.client` stays for jobs. A job runs inside a serving process under the in-process adapter the dummy app uses (`test/dummy/config/application.rb:8` loads Active Job with no adapter configured) or in a worker process that is a serving process under decision 8, so it follows the same rule. No job on main calls `RpmsRpc` today, so this binds future jobs only.
   - Blast radius: a stolen service-account credential is a stolen account on one tenant's instance and no other. Least-privilege keys and rotation are the controls; neither is new to this ADR.
5. **Divisions never separate tenants.** A second division on an instance belongs to the same tenant. Of ADR 0007's division machinery:
   - **to be kept, once built**, as mis-map detection (rpms-rpc#293, open and unbuilt; nothing enumerates divisions today): enumerate divisions at startup; fail closed on a division that maps to no tenant; capture the signed-on `DUZ(2)` and refuse one not allowlisted for the token's tenant. Until it exists, this is a promise, and decision 3 is the only runtime check;
   - **retired**: `(tenant, instance, division)` as a configuration triple that partitions tenants. Configuration is `(tenant, instance)`, and the division allowlist is an attribute of the tenant.
6. **The runtime property: no tenant request reads through an unscoped or wrong-identity client.** In any process that serves a tenant, a read that does not run inside a scope holding that tenant's client for that request's principal is refused, and a send on a client whose identity is not the expected one is refused. A boot check alone does not give this: an implementer could dedupe endpoints while leaving a global client and the sites above unchanged, and the identity of a request would remain "last clinician." The mechanism is ADR 0011 as amended; this ADR makes five requirements of it.
   - **a. No process-global client in a serving process: checked at boot, and enforced by the gem.** A boot check is a snapshot. At the pin, `RpmsRpc.client` is `Fiber[SCOPED_CLIENT_KEY] || configuration.client || raise` evaluated on every call (`core.rb:57`), `Configuration#client=` stays open for the life of the process (`core.rb:33`), and `configure` and `mock!` are public. A boot check proves the slot was empty at boot and nothing after: a later `RpmsRpc.configure { |c| c.client = x }` makes every unscoped call run on `x`, silently. So the boot check is necessary and is not the guarantee. The guarantee needs a **strict mode in the gem** (gem change 1). With strict mode on, `RpmsRpc.client` never falls back to `configuration.client` and raises `NotConfiguredError` outside a scope, and the setter, `configure { |c| c.client = ... }` and `mock!` refuse. A non-serving process (decision 8) reaches the global only through an explicit opt-in that request paths never call. rpms-rpc ADR 0006 made this design acceptable only on those terms ("only acceptable with a strict mode that raises when no session is in scope, with the global reachable solely through an explicit opt-in"), and rpms-rpc#518 shipped the scope without the mode. The engine turns strict mode on when it boots a serving process, and boot fails closed if a global client is already configured. This is the flag ADR 0008's option B called `require_scoped_client`, and under this ADR it is built.
   - **b. The scope belongs to one request and is not inherited.** The scope is opened at the request boundary from the tenant's pool for the request's principal (a service account for a `system/` token), and is cleared on every exit from the request, including an exception. A fiber or thread started inside the scope does **not** inherit it: a child that needs RPMS takes an explicit client or gets `NotConfiguredError`. Inheritance lets a long-lived child keep the first request's client after the request ends. The pool's own keeper is the concrete case: `SessionPool#start_keeper!` starts a `Thread.new` (`session_pool.rb:221`) once and keeps it for the process lifetime, so if it first runs inside a request's scope it holds that user's client from then on.
     - **Measured at the pin.** The scope is stored as `Fiber[SCOPED_CLIENT_KEY]`, and fiber storage is inherited. A probe run against the pinned gem on Ruby 3.4.7, 3.4.9, 4.0.2 and 4.0.6, with identical results, found that `Fiber.new`, `Thread.new`, `Enumerator#next`, `Enumerator::Lazy` and a `Timeout` block all see the scope, that a thread started inside the scope still holds the client after the scope exits, and that an exception exit does clear it. Storing the scope in `Thread.current[...]` (fiber-local, not copied) is invisible to `Fiber.new`, `Thread.new` and `Enumerator#next`, and still visible inside a `Timeout` block, which runs on the calling thread.     - **Gem change 2:** store the scope in `Thread.current[...]`. The cost is that an external enumerator used inside a scope (`.next`) raises `NotConfiguredError`. The gem's only lazy use (`data_mapper.rb:672`) iterates internally, and this repo's `app` and `lib` have no `.next`, `.lazy` or `Enumerator.new`, so nothing breaks today.
     - **The contradicting texts and the spec test.** ADR 0011's amendment says the scope reaches "the fibers and threads it starts" (line 129), the gem's `core.rb:67-69` comment says the same, and the gem's ADR 0006 says the opposite ("any `Thread.new` inside a scope loses it"), which is wrong at the pin. The gem spec `scoped_client_test.rb`, `test_threads_and_fibers_started_in_a_scope_see_it_and_others_do_not` (lines 43-50), asserts inheritance (`assert_same a, Thread.new { RpmsRpc.client }.value`, and the same for `Fiber.new`). It is a spec test, so the spec author rewrites it to assert the opposite, and the builder does not; the builder makes it pass without editing it. ADR 0011's amendment, ADR 0006 and the `core.rb` comment are edited to say one thing.
   - **c. A send-time identity check, on the client the scope holds.** Before an RPC is sent, the connection's authenticated DUZ must equal the request's principal (or, for a `system/` token, the tenant's service-account DUZ for that backend client). A mismatch raises and sends nothing, and records a security event. Checkout-time assertion alone is too early: the live defect was one connection changing identity between calls.
     - **What it reads.** `Client#duz` exists on both broker kinds at the pin (`client.rb:323`; set by `authenticate` and `set_authenticated`, cleared by `clear_authenticated`). Comparing `client.duz` to the expected DUZ immediately before each `call_rpc` needs no gem change for the defect that happened: a second `authenticate` on the same client updates `@duz`. This is the client-side check. It trusts the client's own memory.
     - **What it cannot catch.** A raw `call_rpc("XUS AV CODE", ...)` or a raw sign-on RPC through `call_rpc` re-binds the M process without touching `@duz`. `forbidden_auth_rpcs_test.rb` in the gem is a source scan over `lib`, not a runtime refusal, so that door is open at the pin. **Gem change 3:** the client refuses auth RPCs sent through `call_rpc` at runtime. That is what makes `@duz` trustworthy.
     - **The M-side alternative** (reading the signed-on user from the server, `CIAVCXUS VIMINFO` on CIA or `XUS GET USER INFO` on XWB) costs one RPC per call and is not chosen.
     - **Where it runs.** The check reads `duz` from the client the scope holds, so the audit and identity hook of decision 9 must see the raw client, not a wrapper that hides `duz`.
   - **d. Wrong-tenant scope is refused, not just missing scope.** A call inside tenant B's scope while serving tenant A's token must fail with a tenant-mismatch reason. A missing scope raising is the easy case and does not cover a scope opened for the wrong tenant.
   - **e. One door, with its real reach.** The one-door test ADR 0011 section 7 specifies fails when `RpmsRpc.client`, `RpmsRpc.configure`, `RpmsRpc.mock!` or an `RpmsRpc::` constant is referenced outside the adapter layer (`app/gateways`, `BrokerSession`, the console). The scan is by reference, not by a grep for `Module.method`, so it is the right way to count sites. **Its reach is leaks out of the adapter layer** into controllers, services and models: for example `authentication_service.rb:116` and `:124` and `backend_registry.rb:140` read `RpmsRpc.client` outside the layer and would trip it. **It cannot see a gateway that runs outside a scope**, because every gateway lives inside the permitted layer, so a new gateway in the injected style does not trip it. The property "every gateway runs inside a scope or raises" is carried by 6a (no fallback), 6b (no inheritance) and the runtime tests below, which drive every gateway constant once.
7. **Who may change the mapping, and what a move is.**
   - The tenant-to-instance mapping is operator-held deployment configuration. **Software** can detect a change; it cannot know who edited it or whether it was reviewed. At boot the app compares the loaded mapping with the one it last recorded, and any difference writes a security event with the old and new value. The change takes effect at boot only. **Where "last recorded" lives is stated, and the first-boot case fails closed:** the record is a row in the application database. A serving process (decision 8) that finds the mapping configured and **no recorded mapping** refuses to serve until an operator records it with an explicit command, so a fresh database, a restore or a deleted row cannot silently accept whatever is loaded. This holds in every environment; the test suite records the fixture mapping in its database setup before it boots a serving process. The record command and the database tasks that create the table run as non-serving processes, which is why the first deployment can create the table that holds the record. A person who controls both the database and the config source can still change both; that is a process control.
   - Review by someone other than the author, and protection of the config source, are **process controls** of the deployment (for example branch protection). They are required, and they are not something an acceptance test can prove.
   - A cutover (for example IRIS to YottaDB) is a change of a tenant's active instance, not a second tenant. The tenant keeps its record, its `organization_id` and its stamped rows; the old instance is marked retired in the same change, so a tenant never has two active instances. During dual-run the retired instance is read-only and is not counted against decision 2's uniqueness test while marked retired. The site check in decision 3 cannot tell the retired copy from the new instance; the cutover procedure, not the software, keeps them apart.
8. **Boot does not fail open, in any environment, in a serving process.** Topology validation runs regardless of whether a client was already set and regardless of a blank host. In a serving process, a pre-injected process-global client, or a blank host with tenants configured, is a boot failure in every environment, development included. There is no carve-out for the spike mock and none for the test suite.
   - **Process classes.** A **serving process** answers requests or runs jobs for tenants: the application server (Puma, Falcon, `rails server`), a job worker, and the in-process job adapter inside either. A **non-serving process** is `rails console`, `rails runner`, rake tasks (including `db:create`, `db:migrate`, `db:prepare` and the record-mapping command of decision 7), asset tasks, and the test runner outside a test that boots the application. Nothing in this repo detects the class today (no `Rails::Server`, Puma or job-adapter check exists), so the class is **declared, and an undeclared process is serving**: the engine treats a process as serving unless `LAKERAVEN_EHR_PROCESS=maintenance` is set, which the record command and the database tasks set themselves and which CI sets for its `rails db:create db:migrate` and `db:schema:load` steps (`ci.yml:52`, `:104`, `:161`). Omission therefore fails closed. The declaration is a deployment control: a serving process started with the flag set would be treated as non-serving, and nothing in the software can tell. The name and mechanism are decided here and confirmed in the implementation issue.
   - **What each class may do.** A serving process has no process-global client and runs strict mode (decision 6a). A non-serving process may reach the global only through the explicit opt-in, and signs on as a named identity of its own, which is ADR 0011 section 1's text for the console and rake tasks. ADR 0011 section 1 is amended: `RpmsRpc.client` no longer stays for jobs.
   - **Zero tenants is not a failure.** A serving process with no tenant configured and no host named still boots and logs that no RPMS backend is configured, as the README says (`README.md:62`) and `engine.rb:53-57` comments; no tenant request can reach RPMS. What fails is the combination of tenants configured with a blank host, a pre-injected global client, or an unrecorded mapping (decision 7). `README.md:62` and the `engine.rb:53-57` comment change to say so, and `engine.rb:61` (the early return when a client is already set) is removed.
   - **The development spike mock** (`test/dummy/config/initializers/zz_spike_mock_rpc.rb:20`, which calls `RpmsRpc.mock!` and so installs a global client in a process that serves requests) moves behind the same scope: it opens a scope around each request for the mock client, and configures no global.
   - **The test suite** installs its global with `RpmsRpc.mock!(&BASELINE_MOCK_SEEDS)` (`test_helper.rb:231`), re-installed before every example (`GlobalStoreIsolation`, `test_helper.rb:30-32`). That moves behind a scope too, so `RpmsRpc.configuration.client` is nil during a test unless the test is about boot. This is not a small change: **every** request in the suite, including bearer-token tests that never sign on to RPMS (for example `organization_boundary_test.rb`, which uses a bearer token), then needs a scoped client, and a request with none gets the sign-in page under ADR 0011 section 5. The implementation needs a per-test harness that adopts a mock client into the pool under each test principal's session or token key, and a service-account mock per test tenant. The acceptance tests below depend on that harness, so it is part of the implementation issue and is named here so it is not a surprise. `use_broker` (`test_helper.rb:309-314`) is a separate helper for the registration and scheduling fakes and moves behind a scope as well.

   A boot check and an initializer that sorts last (`zz_` runs after any validation initializer) are not enough on their own; the acceptance test runs the real boot path in a subprocess.
9. **Audit and the identity check live in a gem-level call hook, not in a wrapper around the client.** Every system read records the tenant, the instance, the service-account DUZ, the client application and the request id. `AuditedBroker` today sits on 16 `RpcSupport.broker` sites, and its own header says gem-module calls bypass it and that closing that needs a client hook in the gem, not more wrappers in the engine.
   - **Why not wrap the scoped client.** `AuditedBroker` forwards only `connected?` and `hostname` (`audited_broker.rb:78`) and refuses everything else with `NoMethodError`. The gem modules call much more on `RpmsRpc.client`, and three of those calls are guarded by `respond_to?`, so a wrapper that does not forward them degrades silently, not loudly:
     - `with_context` is skipped (`api/agg.rb:343`, `api/patient.rb:345`, `context_scope.rb:34`), so AGG and patient RPCs run in the sign-on context instead of the one they asked for;
     - `synchronize_wire` falls back to the process-wide `MODULE_WIRE_LOCK` (`core.rb:127-137`), which serializes every user's RPCs through one lock and reverses ADR 0011's consequence that throughput scales with distinct sessions;
     - `call_rpc_lines` falls back to `call_rpc` (`data_mapper.rb:617`, `api/agg.rb:356`), and on XWB the two differ;
     - `call_rpc_global_array` falls back (`api/agg.rb:368`, `api/patient.rb:353`, `api/scheduling.rb:395`, `api/behavioral_health/wire.rb:75`);
     - `duz` and `authenticated?` raise `NoMethodError`, so the identity check of decision 6c could not read the connection's DUZ through the wrapper.

     The session pool also calls `poll` and `disconnect` on the client (`session_pool.rb:264`, `:278`).
   - **The mechanism.** The scope installs the **raw** client, and the pool keeps the raw client, so every method the gem calls is the real one. **Gem change 4:** a call hook the host registers, invoked around each RPC with the client that sends it. The hook performs the audit record and the identity comparison of decision 6c against that client's `duz`, and it runs for every gem-module call from any gateway without touching call sites. The same `AuditedBroker` stays on the 16 `RpcSupport.broker` sites until the hook exists.
   - **The hook's own test.** A test enumerates the public client contract the gem modules call and asserts that a scoped call both records an audit row and takes the same code path as an unhooked call: the context switch happens (`with_context` is not skipped), the per-client wire lock is used and `MODULE_WIRE_LOCK` is not taken, and `call_rpc_lines` and `call_rpc_global_array` reach their own entry points.
   - **Promise, not enforced, until built:** that every read is recorded. Until the hook exists, audit covers the 16 `RpcSupport.broker` sites only. Security events: a refused attempt to reach another tenant, a site-check mismatch, an identity mismatch at send time, and every mapping change.
10. **What stays from ADR 0007 and ADR 0011.** The tenant record with `organization_id` as an immutable foreign key, the session-bound client of ADR 0011, and `tenant_id` stamping on locally held rows, cache keys, jobs and audit rows. Stamping is now needed before a second tenant shares a **process or database**, not before one shares an instance, because one process or database can serve several tenants even when no RPMS instance is shared. The `organization_id` string column is backfilled into the tenant record by ADR 0008 step 1 if that ADR lands, and by the tenant record's own migration otherwise; the request context's `organization` (ADR 0012) resolves to the tenant through that foreign key.
11. **The interim guard is replaced by decision 2.** It is removed when the scoped client is live, as ADR 0007 already says. A sandbox instance is a tenant with its own instance and is not blocked by the guard once it is gone.

## What the software enforces and what it promises

| Property | Enforced by software | Promise or process control |
|---|---|---|
| Two tenants never name the same instance | Load-time key check, within one deployment | Across deployments; round-robin DNS and proxies; the resolver's answer at one moment |
| A swap between different sites | Site check at sign-on (once the gem exposes its fields) | Copies of one site (sandbox, retired, live) |
| A system read runs as that backend client's account | 503 with no RPC when none; send-time identity check on the client's own `duz` | That the account exists on that instance only; host-secret provisioning; a raw auth RPC through `call_rpc` until gem change 3 |
| No unscoped or wrong-tenant read | Boot refuses a global client; strict mode (gem change 1) refuses a fallback and a later setter; a call outside or inside the wrong scope raises; the scope is not inherited (gem change 2) | Until those gem changes land, boot is a snapshot and children inherit the scope; the unwrapped sites are closed only when converted and tested (roughly 105); declaring a process non-serving is a deployment control |
| Mapping changes are visible | Security event at boot; a first boot with no record refuses a serving process | Review of the change; control of the config source and database |
| Divisions map to one tenant | Nothing, until rpms-rpc#293 | The division allowlist, today |
| Every system read is audited | The gem call hook (gem change 4), once built | All reads outside the 16 `RpcSupport.broker` sites, until then |

## Acceptance tests

Each test names how it could pass while its property is broken, and the assertion that closes that. All use two tenants, each with its own mock instance, whose patients have **overlapping DFNs and visibly different fields** (name, date of birth), so the answer's origin is visible from the body. Tests that depend on a gem change (the strict mode, the non-inherited scope, the runtime refusal of auth RPCs, the call hook) are red until that change lands, which is how they gate it. The mock records, for every call it handles, the DUZ the **executing client object** was signed on as at call time.

- **Reused thread, two users, default-provider gateway (the first test).** One reused thread serves two sequential requests as different users, each through a gateway written as `via: default_provider`. Assert that the DUZ the mock stamped on each call equals that request's user. *Passes while broken if* the recorded DUZ is read from the request (the session or the token) and not from the client that executed the call, in which case it matches trivially; so the assertion reads the mock's stamp. It also fails if the scope is left on the thread or the gateway reads a leftover client, because the second request would go out as the first user.
- **A cannot read B, one call per gateway constant.** `RpmsRpc.configuration.client` is nil for the whole test, through the per-test harness of decision 8. A's token reads a patient that exists on both, through **one call per gateway constant** in `app/gateways`, enumerated from the constants, not through one route. Assert on the identity of the client that served each call (its pool key and DUZ), not on a status code or body alone. This enumerates gateways, not the roughly 105 call paths, which have different arguments and cannot be driven generically: the untested methods are the ones behind `via:` and are carried by the strict mode, the non-inherited scope and the call hook. *Passes while broken if* only one route per gateway is converted, if the fixture that is A's instance is also installed as the global (the current helper does exactly that), or if the two instances look alike.
- **Wrong-tenant scope is refused for that reason.** Inside a real request carrying A's token, run a call inside B's scope. Assert it raises, sends nothing, and that the security event's reason is a tenant mismatch. *Passes while broken if* the test opens B's scope with `RpmsRpc.with_client` outside any request, because the refusal then comes from a missing principal and the test is green for the wrong reason.
- **Strict mode holds after boot.** Boot a serving process cleanly, then call `RpmsRpc.configure { |c| c.client = x }` and `RpmsRpc.mock!`. Assert both refuse, and that an unscoped call still raises `NotConfiguredError`. *Passes while broken if* only the boot check is tested, which is the snapshot the gem's fallback defeats.
- **One door, with its real reach.** A test fails if `RpmsRpc.client`, `RpmsRpc.configure`, `RpmsRpc.mock!` or an `RpmsRpc::` constant is referenced outside the adapter layer. It catches leaks out of the layer (`authentication_service.rb`, `backend_registry.rb`) and says nothing about a gateway that runs outside a scope. *Passes while broken if* it is read as covering gateways, which it cannot; the runtime tests above and below carry that property. A grep for `Module.method` would miss both `via:` calls and the `RpmsRpc.client`, `configure` and `mock!` forms, so the scan is by reference.
- **Child does not inherit.** Start a thread, a fiber and an external enumerator (`.next`) inside a scope and assert each raises `NotConfiguredError` when it calls RPMS, that after an exception in the request the scope is cleared, and that `SessionPool#start_keeper!` first called inside a request scope does not capture that request's client. *Passes while broken if* the scope is copied to children, survives an exception, or the keeper is started before the test, so the test starts it inside the scope. It is red at the pin.
- **One endpoint fails load.** Run it against the real boot path for the cases a test can control: the same endpoint, `localhost` against `127.0.0.1` for one listener (and `::1` where the runner has an IPv6 listener; the test says it skipped that case when it did not), a second port on the same host and namespace, and two identifiers with one key reached over CIA and over XWB. A collision is **any shared (address, port) pair**, not equality of the two resolved address sets. The test **does not** claim to exercise DNS aliases or round-robin resolution; those are a deployment control and the ADR says so. *Passes while broken if* broker kind is in the key, or the key compares address sets for equality, so that `localhost` (which resolves to `127.0.0.1` and `::1`) and `127.0.0.1` count as two keys.
- **A swap between different sites is refused at sign-on**, with fixtures whose site answers differ. **A fixture whose answer is entirely empty is refused, not skipped.** The test does not claim to catch copies of one site.
- **No account means 503, no RPC and no fallback.** Run it with a clinician signed in on the same process and with `RpmsRpc.configuration.client` nil. Assert the refusal reason (no account configured, not a connection error, since the broker wrapper also answers 503 for any connection failure) and that no RPC was sent on any pooled client. A job for a tenant with no account fails and does not run.
- **Identity mismatch at send time, within one lease.** Make two calls inside one scope on one checked-out client and, between them, run a second `authenticate` on that client as a different user (the case that changed identity from one call to the next). The second call raises before any RPC is sent. *Passes while broken if* the test changes the DUZ before checkout, because the existing checkout assertion then satisfies it with no send-time check. A second case sends a raw auth RPC through `call_rpc` and asserts the client refuses it at runtime (gem change 3), not through a source scan.
- **The audit hook does not change the call path.** Enumerate the client methods the gem modules call. For a scoped call, assert an audit row is recorded, that `with_context` runs (not skipped), that the per-client wire lock is taken and `MODULE_WIRE_LOCK` is not, and that `call_rpc_lines` and `call_rpc_global_array` reach their own entry points.
- **Boot does not fail open.** Boot the real application in a **subprocess**, once per case, with development as the environment, the spike gate set, and its **own `DATABASE_URL`** (CI creates only the test database). A serving process exits non-zero for each of: a pre-injected global client, a blank host with tenants configured, and a mapping configured with no recorded mapping. The same boot with zero tenants and no host **succeeds** and logs that no RPMS backend is configured. A process declared non-serving (`LAKERAVEN_EHR_PROCESS=maintenance`) boots with the mapping unrecorded, runs `db:create db:migrate`, and runs the record command; an undeclared process is treated as serving. *Passes while broken if* the validator is called in-process with injected settings; that does not prove initializer order.
- **A changed mapping is detected.** Boot against a recorded mapping that differs from the loaded one and assert the security event. Review of the change is a process control and is not tested here.
- **The skipped boundary test is replaced.** `organization_boundary_test.rb:47` is skipped and asserts a status code, the shape this ADR says is insufficient. It is deleted when the identity-based test above lands, not left beside it.
- **Break each check on purpose** and confirm its test goes red. An unverified gate is a comfort, not a control.

## Consequences

- A tenant record must exist before any of this is built (ADR 0007), and the configuration needs a place for the tenant-to-instance mapping and a place for the last recorded mapping. The mapping is operator-held deployment configuration, never a client-registration field.
- ADR 0007's "several entities on one instance" branch becomes dead design. Its table of divergences loses one row.
- **ADR 0007's requirement that the model express a governance domain narrower than the covered entity is not met by this ADR.** An organization serving several governance domains on one instance cannot be expressed as several tenants under decision 1. The requirement is dropped here, deliberately, and declared in Amends. If a domain narrower than the instance is needed, it is an attribute inside one tenant (a scope on the request context), and a design for it is outside this ADR.
- A sandbox or test instance of an entity is a separate tenant. Any state shared between them is cross-tenant state and is treated as such.
- Onboarding a tenant includes provisioning a service account for each backend client and one for its jobs. That is a site task (L3), not an engineering one.
- A tenant on a retired instance during a cutover is allowed only for the dual-run period.
- The gem carries five changes this ADR depends on, owned in rpms-rpc: (1) a strict mode, so `RpmsRpc.client` never falls back to a configured global and the setter, `configure` and `mock!` refuse outside an explicit opt-in; (2) a scope stored where children do not inherit it, with the spec test that asserts the opposite rewritten by the spec author; (3) a runtime refusal of auth RPCs sent through `call_rpc`; (4) a call hook around each RPC, which carries the audit and the identity comparison; (5) a site mapping that exposes `DUZ("AG")` and the station number under their true names. The engine enables strict mode in serving processes.
- The engine changes beyond the gateways: the process-class declaration and the boot rules of decision 8, `README.md:62` and the `engine.rb:53-57` comment (which describe a boot with no backend), the removal of the `engine.rb:61` early return, and the per-test harness for the suite.

## Alternatives rejected

**Support shared instances with row scoping** (the path ADR 0007 left open). The boundary would be derived from RPMS data that carries no tenant, so a single missed filter is a disclosure. The maintainer's position makes the case unsupported rather than merely hard.

**Tenancy is the instance, with no tenant record.** A deployment label is not stable across moves and migrations, which is the reason ADR 0007 kept the tenant first-class. That reasoning still holds, and decision 7 relies on it. The tenant record stays; it is only constrained to one active instance.

**Rely on the boot check alone.** Rejected because it protects a configuration and says nothing about which client a request used; see decision 6.

**Thread an explicit session through every call.** It touches every public gem method (about 240 signatures) and every gateway, and a default argument such as `via: default_provider` resolves the ambient client when the argument is omitted, so an explicit parameter with a default is ambient authority written as a keyword. ADR 0011 as amended chose the scope for that reason; decision 6 keeps the scope and makes its guarantee testable.

**Let a system token ride the shared client.** The state of the code today. It leaves the identity of a system read to whoever signed in last, and ADR 0011 section 6 already rejects it.

## Merge order

ADR 0008 exists only on #630 (open, draft), and ADR 0010 only on #662. ADR 0011 as amended already carries the client mechanism that ADR 0008's option B chose, so #630's choice is already on main in ADR 0011. This ADR can merge first: it decides nothing that rests on ADR 0008's text, and its amendments to ADR 0008 apply only if that ADR lands. If #630 merges first, it needs a note that ADR 0011 carries the mechanism and that this ADR narrows its shared-instance scope. Whether #630 is still wanted at all is the maintainer's call.

## Not verified

- ADR 0011's last-clinician claim for system calls under CIA. Read from the ADR, not re-measured.
- Whether any real deployment has one entity on two instances, and what "two tenants" would mean for it.
- The site counts are a grep and a pattern search over `app` and `lib` at one commit. They can still miss calls made through aliases or string dispatch, which is why the one-door test scans constant references and no acceptance test depends on a count.
- That `Thread.current[...]` storage is enough under the application server's thread reuse: the scope is cleared on every exit and the child-inheritance test covers it, but no probe has run under a real Puma worker. An external enumerator inside a scope raises under that storage, which nothing in `app` or `lib` uses today.
- Whether the client-side DUZ comparison (`Client#duz`) is enough once gem change 3 lands, or an M-side read is wanted on top. It trusts the client's memory and costs nothing; the server-side read costs one RPC per call.
- The count of gateway sites that inject a default (58 in 23 files) was measured at b7dcf2d and not re-measured at 497cecf.
- The per-test harness of decision 8 is a design, not a measured change; its size is unknown until it is attempted.
