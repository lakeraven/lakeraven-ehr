# BPRM 4.00.06 feature inventory

`feature-inventory.tsv` lists every feature of the BPRM 4.00.06 Blazor client, one row per (module, feature), with the screens, writes, reads, rules, authorization and BMW SQL surface each one has.
It is generated, never hand-edited: `bin/bprm_inventory` reads the pinned FOIA source zip as a specification and the rpms-ops client manifest, and the result regenerates byte-identically (lakeraven-ehr#565).
Multi-valued cells are `;`-joined and sorted; the `#` header lines record the source artifact and manifest with their sha256 and the totals.

## Regenerate

    bin/bprm_inventory "$FOIA/GUI Source/bprm0400.06src.zip" "$RPMS_OPS/manifests/clients/bprm-4.00.06.yml"
    bin/bprm_inventory "$FOIA/GUI Source/bprm0400.06src.zip" "$RPMS_OPS/manifests/clients/bprm-4.00.06.yml" --check

`--check` regenerates in memory and exits 1 with a diff summary when the committed file differs; when the zip is not present it prints a skip line and exits 0, so CI stays honest where the drop exists and silent where it does not.
The zip (sha256 `679fa47c...261d6d`) is in the IHS FOIA drop `IHS_RPMS_FOIA_EXTERNAL_20260228`; the manifest is `rpms-ops/manifests/clients/bprm-4.00.06.yml`, which pins that same sha256 (the generator refuses a zip the manifest does not pin); `unzip` must be on `PATH`, and `bundle exec ruby -Itest test/bprm_inventory_test.rb` runs the generator's own test.

## Columns

- `module`, `feature`: `Modules/<Module>/<Module>.{App,Core,Shared}/Features/<Feature>/`, merged across the three projects. A file sitting directly under `Features/` is its own feature, named by its stem minus its role suffix (`PatientQueryHandler.cs` is `Patient`; a leading `I` on an interface is dropped). Files outside `Features/` (startup, `Policies.cs`, `Routes.cs`, shared layout; in Reports the whole module) belong to the `(root)` feature of their module.
- `routes`: the `@page "..."` strings of the feature's routed pages; `pages`: those `.razor` file names.
- `command_handlers` (`*CommandHandler.cs`), `query_handlers` (`*QueryHandler.cs`), `validators` (`*Validator*.cs`): file names prefixed with their project, because a feature's App and Core projects often hold a same-named pair (a client-side proxy and the server handler).
- `policies`: the `Policies.<Name>` constants the feature's pages and handlers reference; `security_keys`: the RPMS security keys those policies require per the modules' `Policies.cs` (`Requirekey`), with `DenyKey` keys as `!KEY`; `RequireMenu` menu options are not listed. A bare `[Authorize]` (signed on, no key) is not a policy and leaves both cells empty.
- `bmw_tables`, `bmw_procedures`: the `BMW.*` / `BMW_BSF_VW.*` tables and `BMW_BSF_SP.*` procedures named in the feature's `.cs` files, comment-stripped, upper-cased for tables. The manifest carries only per-table data (no file names, no procedures), so the generator scans the sources itself and keeps a table only when the manifest lists it; tables it does not list are named in a header line instead.
- `source_files`: how many files the feature has across App, Core and Shared.

## Licence

The BPRM source is read as a specification. Only identifiers leave the generator (file names, routes, policy and key names, SQL object names); no code or text is copied.

## Story map

`story-map.tsv` joins every inventory row to the rpms-ux stories written from it (`story_ids`), or says why it has none (`reason`: site setup, a sign-on step, infrastructure, a lookup with no user goal).
It is keyed by (module, feature) exactly as the inventory is; `bin/bprm_coverage --check` fails when an inventory row has no map row, or a map row names a story that is not in rpms-ux.
The stories themselves live in rpms-ux `docs/product-cycle/STORIES.md` (W01 registration, W02 scheduling, W18 ADT, W19 benefits); this repo only refers to their scenario ids.

## Scenarios, stubs and coverage

The stories are the abstraction; the browser specs under `features/bprm_twin/` are the concrete, one scenario per rpms-ux scenario id, each tagged with it (`@S-REG-02.1`).

- `scenarios.tsv` is the snapshot of rpms-ux's scenario ids (id, story, workflow, persona, title, Given, When, Then, retired) with the rpms-ux commit it came from, so CI needs no rpms-ux checkout and a stale snapshot is visible.
  Regenerate: `bin/bprm_scenarios ~/workspace/rpms-ux` (`--check` compares).
- `features/bprm_twin/stubs/*.feature` are generated by `bin/bprm_stubs`, one pending scenario per id that no hand-written feature under `features/bprm_twin/<workflow>/` drives yet.
  A stub's first step pends and names what it waits on; the story's own Given/When/Then follow, quoted, and the step that matches them pends too, so a stub cannot pass silently (lakeraven-ehr#484).
  To drive a scenario, write it with the same tag in `features/bprm_twin/<workflow>/` and rerun `bin/bprm_stubs`, which drops the stub.
- `bin/bprm_coverage` checks the ids (an id not in rpms-ux, a retired id, or an id on two scenarios fails; a twin scenario with no id fails only with `--strict`), runs the twin through cucumber's JSON formatter, and prints per workflow how many rpms-ux scenarios exist, how many have a spec here, and how many pass, pend, are undefined (steps not written yet) or fail.
  That table is the number quoted for "BPRM parity".
- `legacy-twin-map.md` maps the 16 original twin features (written before the ids existed) to the scenarios they prove; the ones that carry a tag count in the table, usually as undefined until their steps are written, and the rest say why they have no id (lakeraven-ehr#571).

What backs a pass is written at the top of each driven feature file.
Today every driven scenario runs against `RpmsRpc.mock!` (test/test_helper.rb), seeded the way rpms-rpc's own tests seed the same RPCs: a pass proves the screen sends the right writes to the broker and refuses what it must refuse, and asserts nothing about FileMan state on a live RPMS.
That is mock evidence, not parity; parity needs the live tier and the FileMan read-back of `docs/BPRM_PARITY_PLAN.md`.

Run the twin alone: `bundle exec cucumber features/bprm_twin`; one workflow: `bundle exec cucumber features/bprm_twin/w01_registration`.
